It adds Decode Context Parallel \(DCP\), fused FlashKDA kernels, an adaptive speculative token budget delivering roughly 60% better DSpark TTFT, and optional shared-expert sharding saving about 17 GiB per GPU for Kimi-K3. DeepSeek V4 gains end-to-end sparse MLA for plain decode, MTP, and DSpark speculative decoding, plus AMD Quark NVFP4 support and ROCm enablement on gfx11 and gfx950. These changes improve inference performance and expand hardware and software compatibility for vLLM users.

**「Background」** vLLM is an open-source high-throughput LLM inference engine widely used to serve large models in production. Kimi-K3 and DeepSeek V4 are recent large language models that require specialized kernel and scheduling optimizations to achieve efficient decode, context-parallel processing, and speculative decoding.

**「Impact」** vLLM v0.28.0 directly benefits Kimi-K3 and DeepSeek V4 users through faster speculative decoding, lower time-to-first-token, memory savings up to 17 GiB per GPU, and new ROCm support, while the Transformers 5.15.0 bump and bitsandbytes plugin migration require dependency updates.

### [Qwen3.8-Flash-Next: 125B MoE with N-gram Embeddings and 6B Active Parameters](https://qwen.ai/blog?id=qwen3.8-flash-next) ⭐️ 8.0/10

Qwen released Qwen3.8-Flash-Next, an open-weights multimodal mixture-of-experts model combining a 125B-parameter main model with 51B N-gram embeddings and 6B active parameters per token. The design trades additional memory for compute, building on N-gram embedding ideas in recent DeepSeek work and Gemma models. Early community testing covers both QwenCloud API use and self-hosting with GGUF quantizations on a DGX Spark. Because the total parameter count is roughly 176B, commenters question whether practical quantized versions, such as 4-bit weights under 100GB, can run on common 128GB unified-memory systems. The release matters as an open-weights step toward hybrid architectures, with reports of strong coding and regression-fixing performance at low cost.

hackernews · tosh · Aug 26, 12:52 · [Discussion](https://news.ycombinator.com/item?id=49448210)

**「Background」** Large language models commonly use Mixture-of-Experts \(MoE\) to increase parameter counts without a proportional increase in compute, but Qwen3.8-Flash-Next instead combines a 125B-parameter main model with an additional 51B N-gram embedding lookup memory, activating only 6B parameters per token. The N-gram embeddings add capacity with little per-token compute and can be asynchronously offloaded to host memory, since embeddings offer a scaling axis that is less compute-intensive and more offload-friendly than MoE. This architectural direction builds on prior N-gram embedding research, such as a DeepSeek paper from a few months earlier, and has already appeared in a lightweight form in Gemma models.

**「Impact」** For developers evaluating open-weights models, Qwen3.8-Flash-Next offers a low-cost, high-quality option via QwenCloud and a potentially memory-intensive self-host option that may not fit in 128GB unified-memory hardware at reasonable quantization.

**「Community discussion」** Early commenters were impressed by the model&\#x27;s performance on complex coding tasks, including clean merges and regression bisection, quoting about 90M cached input/400k output tokens for $0.45 on QwenCloud. Others questioned the effective size and quantization implications, asked for intuition behind N-gram embeddings, and reported mixed personal preferences versus Qwen 3.8 27B on generated content such as pelicans.

### [Bambu Lab&\#x27;s AGPL Violation Draws Workarounds and Legal Debate](https://lwn.net/SubscriberLink/1089390/46116614cc74b814/) ⭐️ 7.0/10

LWN is reporting on Bambu Lab&\#x27;s ongoing violation of the GNU Affero General Public License \(AGPL\), which has prompted community-driven workarounds and discussions about legal enforcement. The key technical detail is that owners of Bambu printers such as the P2S can avoid Bambu&\#x27;s servers entirely by using LAN mode with OrcaSlicer and the open source reverse-engineered networking plugin open-bamboo-networking, which prevents the printer and slicer from contacting Bambu&\#x27;s cloud. The situation matters because it highlights the difficulty of enforcing copyleft licenses in the maker ecosystem, with some commenters suggesting that legal action through the U.S. Court of International Trade could block imports and pressure the company. No official resolution or lawsuit has been confirmed, and the article itself does not provide concrete dates or specific license provisions beyond characterizing the violation as ongoing.

hackernews · Velocifyer · Aug 26, 17:41 · [Discussion](https://news.ycombinator.com/item?id=49452980)

**「Background」** Bambu Lab, a prominent 3D printer vendor, has been accused of violating the GNU Affero General Public License \(AGPL\) by distributing software derived from AGPL-covered projects such as PrusaSlicer and OrcaSlicer without releasing complete corresponding source code. The Software Freedom Conservancy \(SFC\) has reportedly confirmed two major violations, including a proprietary networking library, libbambu\_networking, that was not fully open-sourced. The AGPL requires that anyone distributing software built on AGPL-licensed code make the complete source code available, and these violations have triggered community efforts to work around Bambu&\#x27;s proprietary servers.

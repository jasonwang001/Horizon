### [Chrome 移除 MV2 扩展，uBlock Origin 下架](https://webiterate.dev/google-removed-extensions-ublock-origin-108/) ⭐️ 7.0/10

Google 已从 Chrome 网上应用店移除 Manifest V2（MV2）扩展，知名广告拦截扩展 uBlock Origin 也在其中。这意味着 Chrome 用户无法再通过官方商店安装或更新 uBlock Origin，依赖 MV2 的扩展生态正被强制迁移到 Manifest V3（MV3）。由于 MV3 对扩展 API 的限制，这类拦截工具的可用性受到直接冲击，因此广告拦截和浏览器选择成为社区关注焦点。目前 Firefox 仍支持 uBlock Origin，且被多位用户视为替代方案。

hackernews · twapi · 8月31日 21:10 · [社区讨论](https://news.ycombinator.com/item?id=49514878)

**「背景」** Chrome 扩展从 Manifest V2 迁移到 Manifest V3 是 Google 为提升扩展安全性和性能而推行的重大变更。自 2024 年起，Google 逐步淘汰 Manifest V2 扩展，并在 2025 年 8 月 31 日从 Chrome 应用商店移除了所有剩余的 Manifest V2 扩展，包括著名的广告拦截工具 uBlock Origin。由于 uBlock Origin 是基于 Manifest V2 构建的，因此在 Chrome 中已不再受支持，Chrome 甚至会提示用户移除该扩展。

**「影响」** Chrome 用户将无法再从 Chrome 网上应用店获取或更新 uBlock Origin，直接受影响的是依赖该扩展进行广告拦截的用户。

**「社区讨论」** 评论中多人表示早已因 MV2 计划转向 Firefox，并称 uBlock Origin 在 Firefox 上表现最佳；也有用户强调广告拦截已成为安全问题，恶意广告对缺乏辨别力的用户尤其危险。

### [互联网集中化与 NAT 的“原罪”之辩](https://dreamstation.systems/personal/ntppost.html) ⭐️ 7.0/10

一篇题为“Internet centralization and the original sin of NAT”的技术随笔，认为 NAT 因应对 IPv4 地址稀缺而成为互联网集中化的早期推手之一：它让设备失去公开端点，并训练用户把“设备-云端-设备”的客户端-服务器模式视为常态。Linux 内核 NAT 实现者 RustyRussell 在评论中承认，自己当年为在单一 IP 上挤入更多连接而放弃端口预留，导致来自不同地址的入站流量无法路由，相当于“穷人防火墙”，但侵蚀了像过去那样自建服务器的能力；其他评论者则指出普通 NAT 在可控时并非邪恶，真正的问题是运营商级 NAT（CGNAT）和家庭网关糟糕的端口转发体验。文章并非新闻事件，而是引发关于 NAT 遗产、安全性与开放互联网代价的历史技术反思。

hackernews · robinpie · 8月31日 02:23 · [社区讨论](https://news.ycombinator.com/item?id=49504905)

**「背景」** 网络地址转换（NAT）最早在 1994 年的 RFC 1631 中正式提出，其初衷是解决 IP 地址枯竭和路由表扩展两大问题，让多个内部设备共享一个公网 IP。NAT 因此成为缓解 IPv4 地址短缺的关键技术，但也让外部主动发起的连接难以直达内部设备，改变了互联网上“人人可架设服务器”的早期模式。这项技术后来被批评为促使互联网走向中心化的早期因素之一，因为它强化了客户端-服务器、设备依赖云端的中枢结构。

**「社区讨论」** 评论中既有对 NAT 加速互联网集中化的认同，也有反驳：有人认为 NAT 让自建服务器不再“运行可执行文件、告诉别人地址”那么简单，并塑造了客户端-服务器思维；另一些人则强调普通 NAT 可以接受，真正受指责的应是运营商级 NAT，而且 NAT 曾在客观上保护了大量未打补丁的脆弱设备。RustyRussell 的“道歉式”评论成为讨论焦点，既解释了技术取舍，也承认了这一设计对公开端点和自托管能力的长期影响。

### [Wrapture：用 wrapt 思路统一测试 stub 与代码追踪](https://simonwillison.net/2026/Aug/31/introducing-wrapture/) ⭐️ 7.0/10

Graham Dumpleton（wrapt、mod\_wsgi 和 New Relic Python agent 的作者）发布了新的 Python 库 Wrapture，将 wrapt 的 monkeypatching 思路扩展为同时适用于测试和追踪：它可以包装任意函数或方法，记录所有调用，或覆盖其返回值。该库既可作为 unittest.mock 的替代方案，也可用于为既有项目添加追踪能力；它内置 OpenTelemetry 支持，并提供基于 TOML 配置的追踪机制（例如 capture=&quot;summary&quot;、observe target 和 jsonlines sink）。目前项目只有数周历史，作者还明确表示 Wrapture 的全部代码和文档都是由 AI 助手在其指导下编写，但这不是 vibe coding，而是由他精心设计的成果。示例展示了 binding\(...\).on\_call.returns\(...\) 式 stub 测试，以及通过 transforms\_result 修改原始方法返回值的测试写法。

rss · Simon Willison · 8月31日 23:59

**「背景」** wrapt 是 Python 中实现函数和方法包装（monkeypatching）的底层库，常用于装饰器、APM agent 和性能追踪工具。Wrapture 在此基础上提供更高级、易用的 API，让同一个“包装”机制既能用于测试替身，也能用于生产环境下的无侵入式可观测性。

**「影响」** 对 Python 开发者而言，Wrapture 提供了一种比 unittest.mock 更贴近真实调用链的测试替身写法，同时让既有项目可以在不改动业务代码的情况下接入追踪和 OpenTelemetry；不过因为项目非常年轻，生产采用前仍需谨慎验证。

### [滑动窗口注意力胜过线性注意力](https://www.reddit.com/r/MachineLearning/comments/1w3j1vw/slidingwindow_attention_beats_linear_on/) ⭐️ 7.0/10

### [GNN 在动态图上可能只是复杂的 MLP：SynthFin-AML 强制因果边界](https://www.reddit.com/r/MachineLearning/comments/1w3imxy/your_gnn_is_probably_just_an_overcomplicated_mlp/) ⭐️ 7.0/10

作者指出，在动态交易图上的标准 GNN 评估存在广泛的时间泄漏问题：如果直接在动态图的静态快照上训练 GNN，模型可能会在训练期间看到未来边，从而“作弊”。为了解决这一问题，他们发布了 SynthFin-AML v10.0 数据集（包含 10 万个节点和 120 万条边），并设计了严格的 3 快照（3-Snapshot）架构，通过按时间窗口（训练图边≤第 7 天、验证图边≤第 8 天、测试图边≤第 10 天）物理切分数据来限制 GNN 的感受野，从而强制执行真正的因果边界。同时，他们修复了“金额分裂作弊”，使欺诈交易和正常零售交易的金额遵循完全相同的对数正态分布（μ=8.517，σ=0.8），并基准测试了严格时间切分下的 LightGBM 与 GraphSAGE：11 个点时间图特征下的 LightGBM 的 PR-AUC 为 0.848，GraphSAGE（归纳式）为 0.881，表明 GNN 在此场景中仅略优于树模型，但这一差距是真实且数学上可靠的，而非泄漏伪影。该基准已作为 PR \#10774 提交给 PyTorch Geometric。

**「背景」** 在反洗钱（AML）等金融交易场景中，图神经网络（GNN）通常用于对交易图进行节点分类或边预测，以检测可疑行为。然而，动态图数据具有时间维度，如果使用标准的随机划分（transductive split）来划分训练和测试集，模型可能会在训练时看到未来的边，导致评估结果虚高。SynthFin-AML 是一个合成金融交易数据集，其设计目的就是通过严格控制时间边界来避免这种“时间泄漏”，从而提供更可靠的评估基准。
